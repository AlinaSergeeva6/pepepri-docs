## Mappings

• Mappings allows us to define how to create a CSV file given another CSV file;

• We can Remove columns, Rename columns, Add calculated column etc.;

• As we map, source drop down is populated with the columns of the CSV file generated by the task;

• As we map, target drop down is populated with “custom” fields of the target object.

**Example:**

Let's say we want only the following columns:

ExternalID, Name, Price, MainCategoryID.

**Step 1.** Set "is\_new\_api" setting to 1;

**Step 2.** Run the task:

The source fields drop down will be poplated with the columns of the CSV file

**Step 3.** Define the mappings:

ExternalID=>ExternalID, Name=>Name, Price=>Price, MainCategoryID=>MainCategoryID

**Step 4.** Set "remove" to 1:

To remove the fields that are not mapped from the final csv

**Step 5.** Run the task:

See that the final CSV contains only the mapped columns.

If you set remove to 0, we will get all the columns

## Join

Join Tab allows you to Join some data (columns) from another task. To turn it on add setting **join** with value **1** It needs to fill some fields **Task/File Name** - Task name like ***Get Data***, etc **Columns -** comma separated columns names like ***ItemName,AccountExternalID*** **Join condition** - condition for Join like ***InternalID=AccountInternalID*** where ***AccountInternalID*** - name of the field from the current task and ***InternalID***\- name of field from the joined file **Fixed width Advanced condition**

Note: order of IDs in join condition matters. First ID must be originated from the external task that you are joining. Consequently, second ID will be from your current data flow task e.g. ID\_of\_external\_task=ID\_of\_internal\_task

in Dataflow task 'Tas Tabs' **j**oin column 'Name ' of task 'Join-1'

## SQL

SQL Tab allows you to run the sql query from External Data Base

To turn it on add setting **is\_sql\_source** with value **1**

It needs to fill some fields**:** Client Type - SQL/ODBC

Connection String - !%sql\_connection%! (you can check it in General Settings)

SQL Statement - there should SQL code, for example: `SELECT ItemNumber ,SequenceNumber ,CustomerNumber ,ComponentItemNumber ,QuantityRequired ,LastPrice FROM PEPPERI_STAGING.dbo.PurchaseHistoryComponent`

## HTTP

There are a lot of possibilities are inside this tab, you can configure it using:

**Method** tab allows you to choose request method

\- GET - POST - PUT - DELETE - PATCH - CONDITIONAL

**Url** – address you will connect to, like *https://api.pepperi.com/v1.0/items*

**Header** This field allows you to specify HTTP request headers like

```
Authorization: Basic a29zdGlhbnR5bi5tQHBlcHBlcmkuY29tOiQyeTRoVQ==
X-Pepperi-ConsumerKey: 0OWMrww5txYDq1r920vGIM9SGsKs1l3Y
```

**Body** This field allows you to specify HTTP request body in JSON or XML format

### Syntax Fields

**{#page\_num#}** - returns page number. Widely used if you want to run task, where you have to get more than one page **{#auto\_num#}** - returns auto-increased number. For example, you want to send POST reuest with JSON body, where you have array of transaction lines in this case you could write in body code like:

```
@@lines
{
    'UUID':'{#new_guid#}',
    'LineNumber': {#auto_num#}
}
@@lines
```

where **@@lines** will allow you to write all of the transaction lines, **{#new\_guid#}** will generate new UUID and **{#auto\_num#}** will return 1,2,3.. for each line

**{#pepperi\_object\_id#} {#sha256\_signed\_query#}** **{#consumer\_key#}** – can be used in header to define your X-Pepperi-ConsumerKey **{#client\_basic\_auth#}** – can be used in header to define your Basic Authorization key in header **{#base64(text)#}** – convert **text** to base64 standard **{#replace(text, find, replace)#}** – replace “find” in “text” with new value “replace” **{#xml\_encode(text)#}** – encode text to XML In some implementations we will need to send XML or HTTP requests with special characters - this will usually happen when there is a text field to which the Pepperi user will enter text values.

In this case, we need to make sure the request (in case it is integrated), will go trough regardless of what the user enters. for this we will use the xml\_encode function. e.g.

we send a request to create a new entity in the ERP system (a customer), and the customer name is "Ben & Jerry's Ice Cream". if we will send in XML or HTTP request the field **$#Name#$**, we will get an error as there is an unsupported character - "&". For this we should use the xml\_encode function in the following way - *{#xml\_encode(****$#Name#$****)#}*

**{#getdate(-30,"yyyy-MM-ddThh:mm:ssZ",day)#}** *-* allows to return date value in selected interval parameters: interval,format,datepart(supported: day,month,year,minute,second,millisecond) the 2 last parameters are optional - format date - if you don't provide it it uses the one from the settings - datepart - default is day
